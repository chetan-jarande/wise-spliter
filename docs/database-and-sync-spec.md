## 1. Core Design Principles

1. **Isolated Custom Postgres Schema (`wise_spliter`):**
   * All cloud tables, views, enums, triggers, RPC functions, and Row-Level Security (RLS) policies reside strictly inside `CREATE SCHEMA wise_spliter;`.
   * Zero application tables are created in `public`.
2. **Local-First Primary Source of Truth:**
   * The client application maintains a complete 1:1 mirror of the user's groups, members, expenses, revisions, settlements, activity logs, comments, receipts, and FX cache in **Dexie.js (IndexedDB)**.
   * Every UI read and write executes locally in `< 1ms` inside an ACID IndexedDB transaction (`db.transaction('rw', ...)`).
3. **Whole-Expense Atomic Revisions (No Unsafe Partial Financial Merging):**
   * Following **Splitwise's financial integrity model**, an Expense's financial state (`total + currency + fx_rate + payers + splits`) is an **indivisible atomic unit**.
   * Concurrent offline edits to the **same expense** are never silently mixed field-by-field (which could produce a total/split combination neither user intended). Instead, each edit carries `base_revision_id` and a **Hybrid Logical Clock (`hlc`)**. If a `base_revision_id` mismatch occurs during sync, both complete revisions are preserved in `expense_revisions`, the latest `hlc` revision becomes active, and `has_unresolved_conflict = true` surfaces a 1-tap **[Keep Mine] / [Keep Theirs] / [Compare Diff]** banner on the bill.
4. **Transparent Group-Wide Activity & Update History (`group_activity_log`):**
   * Every mutation in a group automatically writes a human-readable, structured entry to `group_activity_log` (visible to all members in the group's **Activity / Updates** tab) as well as `expense_revisions` (visible on the specific expense).

## 2. Supabase PostgreSQL Schema (`wise_spliter`)

### 2.1 Schema Initialization & Permissions

Only the Backend API (`service_role`) and `postgres` can reach the schema. Since `0004_tenant_isolation_and_sync.sql`:

```sql
REVOKE ALL ON SCHEMA wise_spliter FROM PUBLIC, anon, authenticated;
GRANT USAGE ON SCHEMA wise_spliter TO service_role, postgres;
REVOKE ALL ON ALL TABLES, SEQUENCES, FUNCTIONS IN SCHEMA wise_spliter FROM PUBLIC, anon, authenticated;
-- default privileges revoked the same way; RLS stays FORCEd on all 8 tables as defense in depth
```

The client never uses PostgREST for this schema; it talks to the API, which calls the RPCs below with the verified actor id. `make migrate-verify` checks that no table or function grant to `anon`/`authenticated` exists.

**Schema notes (the DDL below is the logical model; ids are client-generated `TEXT` matching `^[A-Za-z0-9_-]{1,80}$`).** Migration `0004` adds:
* `profiles.auth_user_id UUID UNIQUE REFERENCES auth.users ON DELETE SET NULL` (profiles are keyed to the auth user), `profiles.token_version` (session revocation), `CHECK (email = lower(email))` on `profiles.email` and `group_members.invited_email`.
* `owner_id` (the creating profile, immutable) on `expenses`, `settlements` and `group_activity_log`.
* Direct (non-group) splits: `wise_spliter.expense_participants (expense_id, participant_id, invited_email, profile_id)` is rebuilt by trigger from `ad_hoc_participants`. A participant is bound to a profile only through that profile's verified email (at write time, or by `claim_members` on a later verified login). Participant ids are scoped to their expense, and new ids must be fresh UUIDs. A direct expense is readable by its owner and its bound participants only; ids and emails the client writes never grant access to anything else.
* Direct settlements carry `expense_id` (the live direct bill they settle); both parties must be participants of that bill and the recorder must be bound to one of them. Either bound party, the bill owner or the recorder may delete it. It is visible to whoever can open the bill while both parties are still on it (`chk_settlements_anchor`). Legacy unanchored rows stay visible to their recorder only.
* `expense_participants.server_seq` changes when a binding is created or changed; an email can be named on at most 2000 unclaimed bills (`trg_unbound_email_cap`), which also bounds `claim_members` (one UPDATE on binding rows of live bills, no bill rows rewritten).
* `groups.invite_code` is generated by the server (`WS-` + 10 hex chars, retried on collision); the client value is ignored.
* `expense_date` / `settled_date` as `DATE`; `hlc` as `TEXT COLLATE "C"` so HLC strings compare byte-wise.
* `server_seq` on every synced table drawn from one sequence `wise_spliter.change_seq`, set on INSERT and bumped by `trg_bump_server_seq` on every UPDATE that changes the row.
* `CHECK` limits on every text and jsonb column (lengths, array counts, `pg_column_size` caps), enums, currency format, and money `<= 2^53-1`.
* Row quotas (`trg_row_caps` + counter table `quota_usage`, O(1) per insert): counted per actor so one member cannot exhaust a shared limit, and over every row ever created (soft-deleted included) so delete-and-recreate cannot grow storage: 500 groups per creator, 50,000 expenses and 50,000 settlements per (scope, owner), 200 revisions per (expense, server-derived actor) (the server-kept v1 snapshot is exempt), 200,000 activity rows per (scope, owner), 50 receipt pointers per (expense, actor), 500 member rows created per (group, actor) with at most 100 active members per group. Counters of hard-deleted groups and bills are removed with them.
* Lock order: `push_mutations`, `claim_members` and `delete_account` take the commit-order lock first, before any row or quota-counter lock, so concurrent writers queue and never deadlock; the `trg_zz_*` seq triggers (named to fire after every check trigger) re-take it for any other write path. Everything done under the lock is O(1) per mutation (indexed lookups, counter rows); heavy validation runs in the API first. The API allows one push in flight per account (a second one gets HTTP 429).
* `trg_expense_member_scope` checks only payer/split ids that are new on an UPDATE, so bills involving since-removed members can still be edited and restored.
* Immutability triggers on `groups.created_by`, `expenses.owner_id`, `settlements.owner_id`, `receipt_attachments.expense_id` and `receipt_attachments.sha256_hex`; `trg_expense_member_scope` requires every payer and split to be an active member of the expense's group, or a listed participant of a direct split.
* Removed: `receipt_attachments.data_url` / `storage_bucket` (always NULL / constant), `profiles.server_seq`, and redundant indexes (see [database-capacity.md](./database-capacity.md)).

### 2.2 Tables & Exact Column Definitions

#### 1. `wise_spliter.profiles`
Stores authenticated users (populated automatically via trigger on `auth.users` after Google OAuth sign-in).

```sql
CREATE TABLE wise_spliter.profiles (
  id UUID PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
  email TEXT NOT NULL UNIQUE, -- normalized lowercase trimmed email
  full_name TEXT NOT NULL,
  avatar_url TEXT,
  default_currency TEXT NOT NULL DEFAULT 'INR',
  upi_id TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  hlc TEXT NOT NULL,
  server_seq BIGINT GENERATED ALWAYS AS IDENTITY
);
CREATE INDEX idx_profiles_email ON wise_spliter.profiles (lower(email));
```

#### 2. `wise_spliter.groups`
Stores shared expense groups. Supports soft-delete (`deleted_at`) for Trash Recovery and editable `base_currency`.

```sql
CREATE TABLE wise_spliter.groups (
  id UUID PRIMARY KEY, -- Client-generated UUIDv7
  name TEXT NOT NULL,
  description TEXT NOT NULL DEFAULT '',
  category TEXT NOT NULL DEFAULT 'trip', -- 'trip' | 'home' | 'couple' | 'friends' | 'other'
  cover_image_url TEXT,
  base_currency TEXT NOT NULL DEFAULT 'INR', -- ISO-4217 code (160+ supported)
  simplify_debts BOOLEAN NOT NULL DEFAULT true,
  default_split_config JSONB, -- Optional saved preset: { mode, member_weights / percentages }
  expense_seq INTEGER NOT NULL DEFAULT 0, -- Monotonic counter used for stateless remainder rotation at expense creation
  invite_code TEXT NOT NULL UNIQUE, -- Shareable token for group invite link
  created_by UUID NOT NULL REFERENCES wise_spliter.profiles(id),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  last_accessed_at TIMESTAMPTZ NOT NULL DEFAULT now(), -- Tracks recent group opens for Home Top-3 list
  deleted_at TIMESTAMPTZ, -- Non-null when in Trash
  deleted_by UUID REFERENCES wise_spliter.profiles(id),
  hlc TEXT NOT NULL,
  server_seq BIGINT GENERATED ALWAYS AS IDENTITY
);
CREATE INDEX idx_groups_server_seq ON wise_spliter.groups (server_seq);
```

#### 3. `wise_spliter.group_members` (Splitwise Unclaimed $\to$ Auto-Linked Member Model)
Allows signed-in users to add friends immediately by **Name + (Optional Gmail / UPI ID)** so bills can be split right away without waiting for friends to install the app. When a friend signs in with Google (matching `invited_email`) or opens the group's `invite_code`, their `user_id` links automatically to their existing `group_members` row.

```sql
CREATE TABLE wise_spliter.group_members (
  id UUID PRIMARY KEY, -- Client-generated UUIDv7 (referenced by expenses & settlements)
  group_id UUID NOT NULL REFERENCES wise_spliter.groups(id) ON DELETE CASCADE,
  user_id UUID REFERENCES wise_spliter.profiles(id) ON DELETE SET NULL, -- NULL until claimed/linked
  invited_email TEXT, -- Normalized lowercase Gmail; auto-links on sign-in when matched
  display_name TEXT NOT NULL,
  avatar_url TEXT,
  upi_id TEXT,
  role TEXT NOT NULL DEFAULT 'member' CHECK (role IN ('admin', 'member')),
  member_order INTEGER NOT NULL DEFAULT 0, -- Deterministic index in group (0..k-1) for remainder rotation
  added_by UUID NOT NULL REFERENCES wise_spliter.profiles(id),
  joined_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  claimed_at TIMESTAMPTZ,
  removed_at TIMESTAMPTZ,
  hlc TEXT NOT NULL,
  server_seq BIGINT GENERATED ALWAYS AS IDENTITY,
  UNIQUE (group_id, user_id),
  UNIQUE (group_id, invited_email)
);
CREATE INDEX idx_group_members_group_user ON wise_spliter.group_members (group_id, user_id);
CREATE INDEX idx_group_members_invited_email ON wise_spliter.group_members (lower(invited_email)) WHERE invited_email IS NOT NULL AND user_id IS NULL;
CREATE INDEX idx_group_members_server_seq ON wise_spliter.group_members (group_id, server_seq);
```

#### 4. `wise_spliter.expenses` (Supports Group-Scoped & Direct Non-Group Splits)
Stores active and soft-deleted bills. `group_id` is **nullable (`UUID NULL`)**: when `group_id IS NOT NULL`, the bill belongs to that group; when `group_id IS NULL` (created via Home Screen Quick-Add without selecting a group), `ad_hoc_participants JSONB` stores the direct participant roster (`[{ id, displayName, invitedEmail, upiId, avatarInitials, memberOrder }]`) and the expense is split purely among those users. Every monetary value is stored in **integer minor units (`BIGINT`)**.

```sql
CREATE TABLE wise_spliter.expenses (
  id UUID PRIMARY KEY, -- Client-generated UUIDv7
  group_id UUID REFERENCES wise_spliter.groups(id) ON DELETE CASCADE, -- NULL for direct non-group expenses
  ad_hoc_participants JSONB NOT NULL DEFAULT '[]', -- Populated when group_id IS NULL
  title TEXT NOT NULL,
  category TEXT NOT NULL DEFAULT 'general',
  tags TEXT[] NOT NULL DEFAULT '{}',
  notes TEXT NOT NULL DEFAULT '',
  expense_date DATE NOT NULL,

  -- Multi-Currency & Splitwise-style FX Audit Fields
  original_currency TEXT NOT NULL, -- Currency entered by user (e.g., 'EUR')
  original_amount_minor BIGINT NOT NULL CHECK (original_amount_minor > 0),
  group_currency TEXT NOT NULL, -- Group's base_currency at calculation time (e.g., 'INR')
  amount_minor BIGINT NOT NULL CHECK (amount_minor > 0), -- Converted amount in group_currency minor units
  fx_rate_scaled BIGINT NOT NULL DEFAULT 100000000 CHECK (fx_rate_scaled > 0), -- Rate * 10^8 (100000000 = 1.0)
  fx_status TEXT NOT NULL DEFAULT 'identity' CHECK (fx_status IN ('identity', 'live', 'cached_offline', 'manual')),
  fx_fetched_at TIMESTAMPTZ,
  fx_audit_note TEXT, -- e.g. 'Converted from €50.00 EUR at 1 EUR = 91.20 INR (2026-11-11)'

  -- Atomic Financial Split & Payer Bundle
  split_mode TEXT NOT NULL CHECK (split_mode IN ('equal', 'exact', 'percentage', 'shares', 'adjustment')),
  rotation_seed INTEGER NOT NULL DEFAULT 0, -- Frozen group expense_seq used when computing equal/share remainders
  payers JSONB NOT NULL,
  /*
    payers schema:
    [
      {
        "member_id": "uuid",
        "paid_minor": 10000,          // in group_currency minor units
        "original_paid_minor": 10000  // in original_currency minor units
      }
    ]
  */
  splits JSONB NOT NULL,
  /*
    splits schema (frozen at save time so deleting other bills never shifts historical paise):
    [
      {
        "member_id": "uuid",
        "included": true,
        "owed_minor": 3334,           // in group_currency minor units
        "original_owed_minor": 3334,  // in original_currency minor units
        "raw_input_value": 1,         // weight, basis_points (e.g. 3333), adjustment_minor, or exact_minor
        "remainder_minor": 1          // 1 if this member received the rotating remainder subunit, else 0
      }
    ]
  */

  -- Revision, Comments, Receipts & Conflict Tracking
  comments JSONB NOT NULL DEFAULT '[]',
  receipts JSONB NOT NULL DEFAULT '[]', -- Structured receipt metadata mirrored with wise_spliter.receipt_attachments
  current_revision_id UUID NOT NULL,
  revision_number INTEGER NOT NULL DEFAULT 1,
  has_unresolved_conflict BOOLEAN NOT NULL DEFAULT false,
  conflict_revision_id UUID, -- Points to the superseded concurrent offline revision in expense_revisions

  created_by UUID NOT NULL REFERENCES wise_spliter.profiles(id),
  updated_by UUID NOT NULL REFERENCES wise_spliter.profiles(id),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  deleted_at TIMESTAMPTZ,
  deleted_by UUID REFERENCES wise_spliter.profiles(id),
  hlc TEXT NOT NULL,
  server_seq BIGINT GENERATED ALWAYS AS IDENTITY
);
CREATE INDEX idx_expenses_group_date ON wise_spliter.expenses (group_id, expense_date DESC);
CREATE INDEX idx_expenses_group_seq ON wise_spliter.expenses (group_id, server_seq);
```

#### 5. `wise_spliter.expense_revisions` (Immutable Per-Expense Edit History & Conflict Store)
Stores the full snapshot and structured diff of every create, edit, delete, restore, currency re-denomination, or concurrent offline conflict on an expense.

```sql
CREATE TABLE wise_spliter.expense_revisions (
  id UUID PRIMARY KEY, -- Client-generated UUIDv7
  expense_id UUID NOT NULL REFERENCES wise_spliter.expenses(id) ON DELETE CASCADE,
  group_id UUID NOT NULL REFERENCES wise_spliter.groups(id) ON DELETE CASCADE,
  revision_number INTEGER NOT NULL,
  base_revision_id UUID, -- The revision the user was viewing when they made this edit
  actor_user_id UUID NOT NULL REFERENCES wise_spliter.profiles(id),
  actor_display_name TEXT NOT NULL,
  action TEXT NOT NULL CHECK (action IN (
    'created', 'updated', 'deleted', 'restored',
    'currency_reconverted', 'conflict_superseded', 'conflict_resolved'
  )),
  changes_json JSONB NOT NULL DEFAULT '[]',
  /*
    changes_json example:
    [
      { "field": "amount_minor", "from": 50000, "to": 60000, "label": "Changed total from ₹500.00 to ₹600.00" },
      { "field": "splits", "label": "Excluded Aman from split" }
    ]
  */
  snapshot JSONB NOT NULL, -- Complete immutable copy of the expense row at this revision
  is_conflict_branch BOOLEAN NOT NULL DEFAULT false,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  hlc TEXT NOT NULL,
  server_seq BIGINT GENERATED ALWAYS AS IDENTITY
);
CREATE INDEX idx_expense_revisions_expense ON wise_spliter.expense_revisions (expense_id, revision_number DESC);
CREATE INDEX idx_expense_revisions_group_seq ON wise_spliter.expense_revisions (group_id, server_seq);
```

### 2.3 Core Schema RPC Functions (`service_role` only)

Every function checks `current_user IN ('service_role', 'postgres')` and has `EXECUTE` granted to `service_role` only.

1. **`schema_health()`**: used by `GET /api/health` and `make migrate-verify` (FORCE RLS count, zero public grants, CHECK/trigger counts, no identity `server_seq`).
2. **`push_mutations(p_actor TEXT, p_mutations JSONB)`**: at most 200 mutations `{ entity, id, op, hlc, data }` (`src/types/sync-contract.ts`), applied parents first (group, member, expense, revision, settlement, activity, receipt pointer), each in its own subtransaction. Per-mutation result `applied` / `stale` / `forbidden` / `invalid`. Authorization is per id with row locks, in the same transaction as the write; nothing is decided from a JS snapshot of the tables.
3. **`pull_changes(p_actor TEXT, p_cursor BIGINT, p_limit INT, p_group TEXT DEFAULT NULL)`**: rows with `server_seq > p_cursor` the actor can read, `ORDER BY server_seq LIMIT p_limit` (max 500), as `{ changes, nextCursor, hasMore, backfillGroupIds, backfillExpenseIds }`. Soft-deleted rows return `deleted: true`; the actor's own membership rows in groups they left return as bare tombstones. `backfillGroupIds` lists groups whose own membership row changed after the cursor (joined, re-added, claimed): their older rows are below the cursor, so the client pages them with `p_group` (`GET /api/ledger/pull?groupId=&cursor=0`) and then continues its main cursor. `backfillExpenseIds` does the same for direct bills the caller was added to or bound to later (`p_expense`, `?expenseId=`, 403 without access).
4. **`claim_members(p_actor TEXT)`**: links unclaimed `group_members` rows whose `invited_email` equals the profile's verified email (exact, lowercase), one per group.
5. **`delete_account(p_actor TEXT)`**: see section 5.3.

Capacity, per-row byte costs and request volumes: [database-capacity.md](./database-capacity.md).

## 3. Local IndexedDB Schema (`Dexie.js`)

The local database on Desktop, iOS, Android, and Web mirrors `wise_spliter` tables 1:1 and adds three local-only operational stores:

```ts
// src/storage/local-db.ts
export class WiseSpliterLocalDB extends Dexie {
  profiles!: Table<LocalProfile, string>;
```

### 3.1 Device-Local Receipt Architecture & Supabase Free-Tier Capacity Math

1. **On-Device Receipt Blobs (`local_receipt_blobs` in Dexie.js IndexedDB):**
   * Compressed WebP receipt images are stored strictly on-device in `local_receipt_blobs` (`uploadedToCloud: false`, `storageBucket: 'local-device-only'`).
   * Zero receipt image bytes are uploaded to Supabase Storage or stored in PostgreSQL (`data_url = NULL` enforced by `0003_local_only_receipt_pointers.sql`). Only a ~180-byte `SHA-256` manifest pointer syncs so online group peers can pull the blob directly over WebRTC (`RTCDataChannel`) per [`./p2p-receipt-mesh-plan.md`](./p2p-receipt-mesh-plan.md).
2. **Footprint and Supabase Free-tier capacity:** measured per-row and per-action costs before and after `0004`, the request model, and the DAU ceilings are in [database-capacity.md](./database-capacity.md). Since `0004` a new expense stores only the expense row: the v1 "created" revision snapshot is not stored at creation (the server keeps the replaced state as a revision the first time the expense changes). The "expense created" activity row is still stored: the feed requirement needs it on every member's device and the client does not derive it yet.

## 4. Multi-User Offline Sync & Conflict Resolution Algorithm

### 4.1 Hybrid Logical Clock (`HLC`) Format
Every device maintains a monotonic **Hybrid Logical Clock** formatted as a lexicographically sortable string:
```
<48-bit-unix-ms-hex>-<16-bit-logical-counter-hex>-<device-node-id>
Example: "019a73e4c210-0001-9f8b2c"
```

### 4.2 Atomic Expense Invariant Enforcement (Client + Backend API + `wise_spliter.push_mutations`)
Before any expense write is accepted (locally in Dexie, in the Backend API Gatekeeper on `:4174`, and in Postgres `wise_spliter.push_mutations`), a strict validation function verifies:
1. $\sum_{p \in \text{payers}} p.\text{paid\_minor} == \text{expense.amount\_minor}$
2. $\sum_{s \in \text{splits}, s.\text{included}} s.\text{owed\_minor} == \text{expense.amount\_minor}$
3. Every `member_id` in `payers` and `splits` belongs to `expense.group_id` (or `expense.ad_hoc_participants` when `group_id IS NULL`).

### 4.3 Push, pull and conflict rules (as implemented)

1. **Dirty entities only:** the client queues one outbox entry per changed entity and pushes debounced batches to `POST /api/ledger/push`; it pulls with `GET /api/ledger/pull?cursor=` on login and app open and merges into Dexie.
2. **Conditional upsert:** a mutation applies only if its `hlc` is newer than the stored row's `hlc` (byte order; at most 60 s in the future). Equal or older is `stale` (with the stored row's `serverHlc`, so the client can advance its clock) and writes nothing, so retries are idempotent and a stale device cannot overwrite newer edits. Expenses and settlements are restored from Trash by an `upsert` with a newer `hlc`. Groups are deleted and restored only by explicit admin ops (`delete`, `restore`); a plain upsert never changes a group's deleted state and a deleted group answers `stale`.
3. **Soft delete:** `op: 'delete'` sets `deleted_at` (groups need an admin) or `removed_at` (members: admin, or the member leaving). Pull returns such rows with `deleted: true`.
4. **Roles:** admins may delete/restore the group, remove members and change roles; any active member may add placeholder members and edit their own row or unclaimed placeholders. `created_by`, `owner_id`, `user_id`, actor ids and actor names are set by the server, never taken from the client.
5. **Concurrent edits (0005):** an expense upsert carries `baseHlc`, the bill's hlc it was edited from. If the stored hlc differs (someone else changed the bill), the server does not overwrite, whatever the hlc order or arrival order: it stores the incoming version as revision `cf_<md5(id:hlc)>` (`conflict_superseded`, `is_conflict_branch`; a direct-bill actor who is not a bound participant is recorded with a NULL `actor_member_id`, never a profile id), sets `has_unresolved_conflict` / `conflict_revision_id` on the bill under a server-minted hlc after both the stored and the incoming one (`next_hlc`), so every device pulls the marker and any edit still based on an older hlc is itself a conflict, and answers `conflict` with the stored bill. The marker is server-owned: inserts never carry one and a normal edit keeps it; keep mine / keep theirs is an upsert with `baseHlc` = the stored hlc, `hasUnresolvedConflict: false` and `conflictRevisionId` naming the conflict it resolves, which clears both. An identical retry of a conflicting push returns the same `conflict` and writes nothing (no revision quota). An exact retry of an applied push (same hlc) is `stale`; a push without `baseHlc` stays last-writer-wins. Deletes are last-writer-wins (recoverable from Trash).
9. **Currency (0005):** a group expense's `group_currency` and a group settlement's `currency` must equal the group's current `base_currency`, else `invalid` with `code: 'currency_mismatch'` and `baseCurrency`. Foreign bills keep `original_currency`, `original_amount_minor` and `fx_rate_scaled` and store `amount_minor` in the base currency. After an admin changes the base currency, a device holding old-currency writes pulls (the group row comes first, since the admin pushes it before the re-converted bills), re-converts and re-pushes; deletes are always allowed. Revision snapshots include `groupCurrency`.
10. **Group bills and payments (0005):** like Splitwise, any active (claimed, not removed) member of the group edits, deletes and restores a group expense or group settlement, whoever recorded it; non-members and removed members get `forbidden`. Ownership (`owner_id`, `created_by_member_id`, comment authors) and scope (group, anchor bill) never change on edit. Admin-only: deleting or restoring the group, changing `base_currency`, rotating the invite code and role changes. Direct bills stay participant-scoped (only the recorder edits a direct settlement). Pulled settlements carry a per-caller `can_edit` (true for group settlements; the recorder only for direct ones). `settled_date` is between 2000-01-01 and tomorrow (UTC).
12. **Payee VPAs (0005):** a claimed member's `upi_id` changes only by that user (admins included get `forbidden`). Any active member may change an unclaimed placeholder's `upi_id`; on a direct bill only the bill owner or that participant once bound may change a participant's `upiId`. Every such change writes a server-authored `group_activity_log` row (`action = 'upi_changed'`, masked old and new values such as `ka***@okaxis`), visible to the group or the bill's participants.
11. **Invite codes (0005):** codes are only server-minted `WS-` plus 10 hex digits (40 bits; `chk_groups_invite_code`; older guessable codes were re-minted by 0005). `POST /api/groups/join {code}` runs `join_group`, which re-reads the group under the commit-order lock: it binds the caller's unclaimed placeholder carrying their verified email, else revives their own earlier member row only if they left it themselves (`removed_by` = them; as a plain member while the group has an admin; within the 100-active-member cap), else adds a member, and returns `groupId` for a `?groupId=` backfill. A user an admin removed gets 403 ("An admin removed you from this group; ask them to add you back"); an admin re-adds them with an ordinary member upsert (`removedAt` null, which clears `removed_by`). Limits: 10 attempts per account and 30 per IP per 10 minutes (per API process), and 20 failed codes per account per UTC day in `quota_usage` (kind `join_fail`, holds across replicas). Admins rotate the code with a group upsert `rotateInviteCode: true`. Leaving is a `group_member` delete of one's own row; the last admin cannot leave or step down while other accounts remain.
6. **Commit order equals `server_seq` order:** every writer takes `pg_advisory_xact_lock(7735001)` before drawing a seq (the RPCs at entry, and the `trg_assign_server_seq` / `trg_bump_server_seq` triggers for any other path) and holds it until commit, so a cursor can never step over a lower seq that commits later. The ceiling is one global write lock (a few hundred write transactions per second); per-group sequences or snapshot fencing are the upgrade path.
8. **Time box:** `push_mutations` sets `lock_timeout = 2s` and aborts a batch that runs past 2 s, or hits a deadlock, as a whole (HTTP 503, retried by the client). The caller check uses the `role` setting (PostgREST's JWT role), because inside `SECURITY DEFINER` `current_user` is always the owner.
7. **Group recency:** `last_accessed_at` is per-device; a group push that changes only it is acknowledged without a write, so members do not re-pull the group row for every expense.

### 4.4 Claiming placeholder members
On every verified login (`POST /api/auth/google` with a confirmed Google identity, or `POST /api/auth/login` with a confirmed email and an existing profile) the API calls `wise_spliter.claim_members(profile_id)`, which sets `user_id` on unclaimed rows whose `invited_email` equals the profile email exactly. Access to a group always comes from the claimed `user_id`; an unclaimed email never grants access.

## 5. Security & Row-Level Security (RLS) Architecture

Every table in `wise_spliter` has `ALTER TABLE ... ENABLE ROW LEVEL SECURITY;` and `FORCE ROW LEVEL SECURITY;`.

### 5.1 Caller-Scoped Security-Definer Membership Helpers (introduced in `0002`, tightened in `0004`)
`0004` redefines the helpers below: membership is only an active row with `user_id = current_profile_id()`, where `current_profile_id()` resolves `profiles.auth_user_id = auth.uid()`. The creator and invited-email branches shown here were removed.

All 8 tables enforce `ENABLE ROW LEVEL SECURITY` and `FORCE ROW LEVEL SECURITY`. Membership predicates resolve verified identity strictly from `auth.users` via `(SELECT auth.uid())` (`SET search_path = ''`, never trusting editable `user_metadata` or deprecated `auth.role()`) and check `gm.removed_at IS NULL` so soft-removed members immediately lose access:

```sql
CREATE OR REPLACE FUNCTION wise_spliter.is_group_member(p_group_id TEXT)
RETURNS BOOLEAN
LANGUAGE sql
SECURITY DEFINER
STABLE
SET search_path = ''
AS $$
  SELECT CASE
    WHEN (SELECT auth.uid()) IS NULL OR p_group_id IS NULL THEN false
    ELSE EXISTS (
      SELECT 1 FROM wise_spliter.groups g
      WHERE g.id = p_group_id
        AND g.created_by IN ((SELECT wise_spliter.current_profile_id()), (SELECT auth.uid())::text)
    ) OR EXISTS (
      SELECT 1 FROM wise_spliter.group_members gm
      WHERE gm.group_id = p_group_id
        AND gm.removed_at IS NULL
        AND (
          gm.user_id IN ((SELECT wise_spliter.current_profile_id()), (SELECT auth.uid())::text)
          OR lower(gm.invited_email) = (SELECT wise_spliter.current_auth_email())
        )
    )
  END;
$$;
```

### 5.2 RLS (defense in depth)
RLS is FORCEd on every table with **no policies**, which denies every row to any role without `BYPASSRLS` even if a grant reappears. The earlier membership helpers and policies were dropped in `0004` because they duplicated the RPC rules with weaker logic. Every `wise_spliter` function has `EXECUTE` revoked from `PUBLIC`, `anon` and `authenticated` after each migration (the runner does it per migration; global default privileges are shared with the other app and are not changed). The old `storage.objects` receipt policy was dropped because receipts never reach Storage.

### 5.3 Account deletion (`POST /api/account/delete`, `delete_account`)
* The user's `group_members` rows are kept (balances of the other members still add up) but lose `user_id`, `invited_email`, `upi_id`, and get the display name "Deleted user"; actor names in revisions and activity become "Deleted user".
* Groups that no longer have any active claimed member are deleted with their rows.
* Direct splits only the user could see are deleted. Shared direct splits (anyone else named or bound) and the settlements anchored to them are kept, with the user scrubbed from the participant list, so every other person's balances are identical before and after.
* Rows kept for others get a tombstoned owner (`deleted_<random>`), so a profile later re-created with the same id has no rights over them.
* The profile is deleted, which invalidates every session token. `token_version` starts at a random value, so a profile re-created with the same id does not revive old tokens. `auth.users` is shared with another app and is never deleted.
